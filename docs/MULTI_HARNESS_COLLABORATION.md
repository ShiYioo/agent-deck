# AgentDeck 多 Harness 共享会话与协作技术方案

调研日期：2026-10-11。状态：设计提案，未实现或完成跨供应商联调。

## 1. 结论

**多个 harness 可以共享一个 AgentDeck 会话，但不必、也不应强行共享同一个原生会话文件。接力不必每次调用模型压缩总结。**

推荐架构：一个逻辑会话 + 可追溯事件账本 + 多个原生会话绑定 + 增量上下文同步 + 版本化共享任务状态。

这里的“共享”指用户目标、公开对话、任务状态和工作成果共享；不承诺移植模型内部状态、私有推理、供应商缓存或任意原生工具调用协议。它也不意味着每个 harness 每轮都读取完整历史。

优先实现顺序：

1. 不分裂的逻辑会话和无强制总结接力。
2. 原生会话恢复、增量同步和历史按需检索。
3. 主执行者 + 只读专家的混合协作。
4. 隔离工作树下的并行实施，以及受控递归委派实验。

## 2. 当前代码基础与问题

以下为调研时工作区观察，不将正在变化的字段视为已经完成的产品能力：

| 位置 | 当前观察 | 对方案的意义 |
| --- | --- | --- |

还需确认两个契约：交接必须携带用户本轮最新输入；切换 harness 不得自动扩大审批或文件权限。旧接力 prompt 不是当前用户输入的替代品。

## 3. 三种“同一会话”必须区分

| 层次 | 能否统一 | 说明 |
| --- | --- | --- |
| 产品逻辑会话 | 应当统一 | 一个标题、一个用户输入流、一条可追溯时间线 |
| 公开协作状态 | 可以统一 | 目标、约束、决策、计划、证据、消息和成果引用 |
| 原生执行会话 | 分别保留 | Codex thread、OpenCode session、sidecar session 等各自负责原生恢复 |

建议关系：一个 conversation_id 对应多个 runtime binding；每个 binding 可以有多次执行任务，也可以因分支、损坏或版本不兼容而更换。

“共享同一个 JSONL 文件，让不同 harness 随便读写”不作为正式方案。它缺乏格式、写入顺序、工具语义和恢复版本的一致性保证。

## 4. 已核实的技术与边界

### 4.1 原生服务：最直接的上下文注入与续接

- Codex 官方 OpenAI documentation 的 App Server 提供 thread/resume、thread/fork、thread/read；thread/inject_items 可向已加载线程追加 Responses API 历史项，不启动用户 turn，并持久化到 rollout。[S1]
- OpenCode Server 提供 session、历史消息、fork、abort、SSE；消息接口包含 noReply 参数，可作为“预先同步内容而不立即生成回复”的候选能力。它不是任意外部 assistant/tool 历史的通用导入承诺。[S2]
- 对 ZCode，当前仓库只能证明已有 CLI 适配；未核实其通用历史导入或 ACP 能力，不应在方案里宣称已经支持。

落地要求：从本机版本生成或读取 schema，做能力探测和最小联调。Codex 文档含实验性接口/传输说明；优先考虑本地 stdio，不能假设任意已安装版本都支持当前网页里的接口。OpenCode 当前网页也不能代替本地服务器版本与 OpenAPI 的核验。

### 4.2 ACP：统一客户端到 harness 的接口

ACP 规范定义 session/new、session/load，并按能力支持其他生命周期操作；load 用于恢复并向客户端回放历史，resume 用于不回放历史的重连。[S3]

**ACP 统一的是连接和会话操作，不保证 A harness 的 sessionId 能直接被 B harness 加载。** AgentDeck 仍要保存跨 harness 的公共事实源和适配映射。支持矩阵必须由各 agent 的初始化能力决定。

### 4.3 MCP：提供共享历史、任务板和成果查询

MCP resources 可以暴露上下文数据，是否加入模型上下文由宿主决定；订阅也是可选能力。[S4]

适合让 AgentDeck 提供统一的历史检索、证据读取、任务查询和专家请求工具。MCP 是共享数据/工具的入口，不会自动使多个模型拥有相同记忆。对只支持工具、不自动读取资源的 harness，应提供工具查询路径。

### 4.4 A2A：远端智能体协作的标准边界

本次读取的 A2A 官方规范显示最新发布版本为 1.0.0，定义 Message、Task、Artifact、Agent Card 和 contextId，面向独立且内部可不透明的 agent 系统。[S5]

适合未来连接远程专家或云端执行器，不必在第一版本地桌面架构里引入完整网络协议。contextId 是逻辑关联，不是共享模型内存；规范也不保证消息历史覆盖所有交互，关键事实仍要由 AgentDeck 自行持久化。

### 4.5 状态驱动 handoff：成熟的编排方式

LangChain/LangGraph 官方文档将 handoff 描述为持久状态驱动的路由或配置变化，并要求跨 agent 传递消息时处理上下文选择及工具调用/返回配对。[S6]

可借鉴状态机和检查点语义，不必为了该模式把当前 Rust 编排整体迁移到 Python 或 LangGraph。

### 4.6 新探索：RLM 与 Recursive Agent Harnesses

RLM 将长输入放到外部环境，由模型按需检查、分解和递归处理片段，而非始终塞入一个 prompt；论文首次提交于 2025-12-31，本次读取为 2026-05-11 的 v3。[S7]

Recursive Agent Harnesses 于 2026-06-11 提交，递归单元进一步成为带文件、代码执行和计划能力的完整 harness，并通过脚本组织子 harness 与结构化子任务。[S8]

这是有研究证据的探索方向，不是已经证明适合 AgentDeck 所有编码任务的标准方案。其长上下文基准结果不能直接推导出真实仓库任务的质量、费用或延迟收益。

## 5. 推荐架构

```text
用户输入 / 当前目标与约束
             |
      AgentDeck Conversation
             |
   事件账本 + 版本化任务板 + 成果库
             |
      上下文编译与协作调度
        /        |        \
  Codex绑定  OpenCode绑定  ZCode/sidecar绑定
        \        |        /
          统一可追溯时间线
```

这是“一个会话，多个上下文视图”，不是“把整个 prompt 广播给所有模型”。

### 5.1 数据模型

| 对象 | 建议内容 |
| --- | --- |
| Conversation | 独立逻辑身份、项目、当前目标版本、主分支、活动执行者、权限策略 |
| Runtime binding | harness、原生句柄、版本、能力、分支、最近已确认同步的事件范围 |
| Event | 全局标识、会话顺序、父事件、执行者、角色、事件种类、公开正文、原始载荷引用 |
| Task state | 用户约束、阶段、负责人、依赖、决策、未解决问题、验收条件、版本号 |
| Artifact | 原文、diff、日志、截图、测试证据及其 hash、生成版本、访问策略 |
| Context delivery | 给哪个 binding 传了什么、采用何种映射、覆盖哪些事件、确认状态、token 估算 |
| Context checkpoint | 可选总结及其来源区间、生成模型、有效范围、原文回查入口 |

原始事件保留，流式片段归并为可读消息；不要重复同步快照。用户原话不依赖助手回复保存。私有内部日志、密钥和不该跨供应商的数据默认不共享。

### 5.2 一个具体的 A → B → A 流程

1. ZCode 在会话 C 内完成任务到事件 120；用户新增“先让 Codex 检查，不要修改”。
2. AgentDeck 固定最新用户要求、事件边界和工作区版本，安排 Codex 只读检查。
3. 如果 Codex 已有绑定且已同步到事件 80，恢复它，只补充它缺少的相关公开事件与本轮要求；首次加入则提供符合预算的完整公开记录或按需查询入口。
4. Codex 返回问题列表、文件定位和检查证据，写入同一会话 C，不另起侧栏聊天。
5. 返回 ZCode 时，恢复其原生句柄，补充新的用户要求、Codex 发现和相关工作区变化，不重新总结前 120 个事件。
6. ZCode 修复、测试并记录成果版本，用户仍只面对会话 C。

该流程不需要独立总结模型。恢复、补充上下文及下一次正常模型推理仍可能产生延迟和费用。

## 6. 总结不是必经步骤：上下文编译策略

选择顺序建议：

1. 已有有效原生绑定：恢复 + 缺失增量。
2. 首次接入且公开历史符合预算：映射完整公开历史；无法进行原生导入时，作为带来源的历史资料注入。
3. 历史很长：当前目标/约束 + 最近原文 + 决策/证据索引 + 可查询历史。
4. 查询与上下文仍不足：按需生成阶段检查点，保留全部原始记录。

上下文可用预算 = 模型窗口 - 系统/工具开销 - 当前输入 - 输出预留 - 安全余量。不要继续以固定字符数代替所有模型的 token 预算；不知道窗口时采用保守配置并显式标记。

任务状态板本身是一种信息选择，但不等于“每次接力先额外调用模型做有损总结”。模型总结只能是可替换的辅助视图，不是唯一历史，也不是正确性的依据。

### 6.1 保真与兼容规则

- 跨 harness 内容带执行者、时间、版本和原文引用，不伪装为接收方自己做过的工作。
- 历史中的指令按来源分类；外部 agent 和工具输出不能覆盖用户约束或提高权限。
- 不向新 harness 盲目复制原始 toolCallId、未配对调用或未知工具 schema。
- 不支持导入时，工具执行结果作为已完成的证据资料传入；不能因回放记录再次执行工具。
- A 返回时不仅补协作消息，还要标记 A 曾读取文件已经变化，要求核对旧结论。
- 分支上下文按分支可见性同步，不能只按一个全局数字混合所有分支。
- “已交付”不等于模型理解或接受；同步确认状态需要与执行结果分开。

## 7. 四种协作模式

| 模式 | 机制 | 建议定位 |
| --- | --- | --- |
| 无总结顺序接力 | 原生恢复、公开历史或增量投影 | 第一优先级，解决额度故障与自由切换 |
| 主执行者 + 只读专家 | 主执行者保有控制权，按需请求其他 harness 审查或回答局部问题 | 第二优先级，默认协作形态 |
| 共享任务板 + 隔离并行实施 | 每个子任务有依赖、负责人、独立 worktree；成果经核验再集成 | 明确模块边界后开放 |
| 受控 harness 递归 | harness 请求子任务，AgentDeck 审核预算和范围后派发，返回结构化成果 | 实验功能，不开放无限自发递归 |

第二种模式通常不需要真正“移交整个会话”：Codex 可以只审查一个 diff，OpenCode 可以只分析一个失败测试；结果回到主执行者原来的上下文。

任务板建议由 AgentDeck 做版本和冲突仲裁，agent 提交更新请求，不让多个进程直接覆盖同一个 Markdown 文件。事实、推测、待验证项和用户决定分别记录；相互矛盾的结论保留来源，不通过“最后写入者获胜”决定真伪。

实验递归初始建议：深度最多 1、每阶段最多 2 个子任务、明确时间/token/费用上限；禁止子任务再次委派，失败或证据不足交还主执行者。以上为提案参数，需通过评测调整。

## 8. 文件一致性、权限与恢复

- 同一可写目录默认只允许一个活动写入者。通过调度租约、进程生命周期和实际工具/沙箱策略协同约束；仅靠 prompt 写“只读”不能作为安全保证。
- 并行写入必须隔离 worktree。记录 base commit、未提交修改和成果 patch；集成由单一执行者负责，并重新跑验收。
- 只读检查绑定明确的工作区版本；正在变化的文件不是稳定快照。历史 diff 和测试通过不能证明最新文件仍然通过。
- 接力前停止或确认旧写入者结束；超时取消后检查进程树和可能留下的副作用，再决定是否派给新执行者。
- 审批仍按具体运行和工具调用绑定，不能因共享聊天而把 A 的批准自动授予 B。
- 跨供应商前过滤密钥及敏感信息，保留用户设定的数据边界；接入远端专家需单独授权。
- 账本采用可去重的事件写入、检查点和同步确认；承认外部副作用可能需要人工或工具核对，不宣称通用 exactly-once 执行。
- 崩溃恢复后先恢复任务状态、binding 和未完成审批；不自动重跑不明确是否已经完成的修改命令。

## 9. UI 契约

用户只看到一个聊天标题和一条主时间线。消息标注来自哪个 harness；接力显示接收方、原因与上下文同步方式，不把内部传输 prompt 伪装成用户新消息。

主执行者、只读协作者和并行子任务可在执行详情中查看。切换执行者、停止协作、撤销待执行任务和查询证据应明确可操作；不要求用户手动复制总结。

保留当前会话的草稿、队列、项目、目录和权限。当前用户要求比旧计划与旧总结优先；检查点只说明覆盖范围，不显示为新的权威指令。

## 10. 分阶段落地

### 第一阶段：统一身份，移除强制总结依赖

核对并补齐已有 conversation_id 方向；原生句柄放到独立 binding。接力支持“恢复+增量”或“预算内公开原文”，现有 AI 总结变成可选策略。旧数据不能仅凭相同目录推断同一会话。

完成标准：A → B → A 仍只有一个侧栏会话；接力不依赖单独的总结 API Key；最新用户要求、工作目录、权限与未完成任务不丢失。

### 第二阶段：服务适配与外部上下文

验证本机 Codex App Server、OpenCode Server 和 ACP 能力；保留 CLI 适配 fallback。建立上下文编译、交付记录和原文查询。先用 SQLite 及可用的全文检索，确有必要再增加向量检索。

完成标准：短会话不调用总结；长会话可回查早期约束和证据；不存在重放工具执行、重复消息或不兼容的孤立工具返回。

### 第三阶段：专家协作与并行成果

在现有 collaboration 状态机上扩展点对点专家请求与结构化验收；随后引入独立 worktree、任务依赖和成果合并。

完成标准：审查方不修改主目录；所有测试证据关联成果版本；文件冲突和结论分歧可追溯，不静默覆盖。

### 第四阶段：可控自适应编排

通过真实仓库任务评测是否需要自动选择专家、RLM 式历史查询或 RAH 式递归子任务。按质量/成本收益开放，避免为“多 agent”而多 agent。

## 11. 验证与取舍

对比四条基线：当前强制总结接力、预算内完整公开历史、恢复+增量、任务板+按需检索。单 agent 完成同类任务也作为基线，防止协作增加成本却降低质量。

测试覆盖：早期约束隐藏在长历史、连续多次切换、总结不可用、原生恢复句柄损坏、分支选择、未提交修改、工具进行中切换、审批等待、旧进程残留、敏感信息、网络中断与进程崩溃。

指标：任务通过率、早期约束召回、重复工作率、接力前模型调用数、到接收方首次有效行动的 P50/P95 延迟、总 token/费用、冲突数量、恢复成功率。先采集实测基线，不承诺未测量的加速倍数。

方案保留两种诚实边界：

1. 存储层可以保留完整公开原文，模型工作上下文仍然可能受窗口、检索和原生 compaction 限制。
2. 不额外总结可以消除一段串行等待，但全量原文可能增加下一轮 token 费用；需要由上下文预算和评测选择。

## 12. 决策建议

**采用“逻辑会话主权在 AgentDeck，原生执行会话留在各 harness”的路线。**

近期做无强制总结的顺序接力和增量同步；中期让当前主执行者按需调用只读专家；长期再做隔离并行、远端 A2A 接入和受控递归。MCP/ACP/A2A 各自解决不同边界，不是互相替代的万能共享记忆协议。
